## 1. Cel i granice

Cel: z zakończonej, autoryzowanej rozmowy Voice AI przygotować audytowalne **dowody zachowań i kompetencji**, ocenę per kryterium oraz raport dla człowieka. Nie oceniać głosu, akcentu, emocji, tempa mówienia, domniemanej osobowości ani cech chronionych. Nie podejmować automatycznych decyzji zatrudnij/odrzuć. Nie używać tego modułu jako platformy telefonicznej.

### Przepływ

SC-006 reviewed screening + SC-008 current human shortlist
→ SC-010 verified contact/approval + przyszłe SC-010-C single-use dispatch
→ SC-012 approved/versioned interview plan
→ SC-011 provider events + SC-012 conversation execution
→ SC-013 private transcript ingestion and integrity checking
→ evidence extraction/criterion ratings (AI worker)
→ human review and immutable overrides
→ SC-015 consolidated WERYFIKACJA report (osobny task).

Dane zagregowane w raportach nie mogą zastąpić kontroli dowodów oraz ostatecznej decyzji człowieka.

## 2. Prerequisites (fail closed)

Nie wolno uruchamiać analizy tylko na podstawie providerCallId. Serwer musi sprawdzić:
- tenant, recruitment, application, candidate i rozmowę należące do jednej firmy; composite FKs i RLS;
- rozmowę rzeczywiście **ukończoną**, powiązaną z dokładną aktywną/archiwalną wersją zatwierdzonego planu i zaufanym zdarzeniem providera;
- brak wycofania praw i brak blokady retencji, legalną podstawę przetwarzania transkryptu, wersję notice i obowiązującą politykę; osobna zgoda na nagrywanie tam, gdzie wymagana;
- spójność wersji wejścia; źródło nieaktualne może być historycznie audytowalne, ale nie może udawać bieżącego wyniku;
- transkrypt dostarczony zweryfikowanym kanałem i powiązany z wywołaniem, a nie przyjęty bezpośrednio od przeglądarki.

Bieżące SC-010 B1/B2 nie posiada production dispatch; architektura pozostaje nieaktywna do czasu review i osobnej akceptacji.

## 3. Rozdzielenie zaufania, danych i providerów

1. Provider transport (SC-011) zwraca tylko podpisane callbacki/identyfikatory rozmów. Zewnętrzny provider nie może pisać wyników do tabel rekrutacji.
2. Signed webhook intake: autoryzacja dostawcy, raw-byte signature, timestamp/replay, account and tenant binding, body-size limit, idempotent provider event ID. Niedopasowany callback -> brak zapisów; brak pewnego zakończenia -> reconciliation, nie fikcyjne completed.
3. Transcript ingestion worker: minimalny transkrypt, bez nagrania o ile opcjonalna osobna polityka go nie dopuszcza. Dane kontaktowe oraz oryginalne CV nie są przekazywane do modelu analizującego.
4. Analysis worker (oddzielna minimalna capability NOLOGIN, bez `service_role` w przeglądarce), claim/lease/complete/fail, niskie uprawnienia do jednego zakresu. API user-facing nie posiada claim/complete/fail.
5. Review rekrutera: tylko przez tenant-checked RPC z wersjonowaniem i compare-and-swap. Reviewer nie przepisuje wyniku AI; dopisuje immutable override.

Treść transkryptu to niezaufane dane wejściowe: prompt injection wypowiedziany przez kandydata nie może zmienić instrukcji analizy, schematu, polityki ani zakresu narzędzi. Analiza bez tool calling i bez otwartego dostępu do internetu.

## 5. Transcript contract, evidence and rating

Versioned transcript input:
- `schema_version`, `voice_interview_id`, `provider_event_id`, `language`, `source_type`, `transcript_segments`, `transcript_sha256`, source plan version.
- Segments have immutable `segment_id`, `speaker = interviewer|candidate`, `start_ms`, `end_ms`, `text`. Timecodes optional ONLY if provider cannot supply them; ordered monotonic transcript positions always required. Exclude entire system/provider payload and other media.
- A canonical normalized transcript text and UTF-16 index offsets must be snapshotted and protected by fingerprint. Model receives only **candidate lines**, criterion definitions and consent-minimized approved plan context. No raw phone/email, CV text, unrelated prior interviews or employer secrets.
- Evidence for each rating: `{segment_id, start_utf16, end_utf16, quote}`, exact substring validation and speaker=candidate. Max 5 quotes per criterion, each bounded by the versioned UTF-16 and byte limits in V7.7; no invented quotes and no model-authored citations lacking offsets.
- Rating enum shared with existing screening: `insufficient_data | below | meets | above`. `insufficient_data` remains NULL in numeric scoring; no forced zero. Meaning of below/meets/above anchored to **approved version of criterion rubric**, not a probabilistic impression.
- Store what the candidate actually said separately from AI interpretation. Silence, unintelligible audio, disconnect, lack of opportunity to answer and model/provider errors mean unknown/insufficient_data, never an automatic negative rating.

Versioned policies: `voice-analysis-v1` (schema/prompt/criterion mapping) and `voice-review-v1` (human-review semantics). Changes to policy/model generate new analysis version, never mutate previous results.

## 6. Machine of states and concurrency

Interview: `planned -> authorized -> provider_pending -> in_progress -> completed | incomplete | cancelled | failed | unknown`.

Analysis: `pending -> processing -> completed | failed | cancelled`; independent `stale_at/stale_reason` and `review_version`. Running a new attempt never overwrites previously completed results; only completed, reviewed, current analysis may appear as current in reports.

One logical analysis per source fingerprint + contract hash; multiple provider attempts remain nested attempts, each has lease generation and idempotency key. A lost/expired lease cannot finalize; old webhook cannot roll terminal status backwards. Accept completed recording/transcript only from trusted event + correlation; missing callback -> reconciliation, no retry dial.

Lock order and optimistic versions must be checked against SC-006, SC-008, SC-010. Concurrency tests must cover review vs new transcript, review vs new plan, source change vs finalize, cancellation vs callback, old lease vs retry and cross-tenant concurrent access. Use controlled conflict (409), not implicit last-write-wins.

## 7. Human review and report

Recruiter sees: expected criterion/rubric, approved question, transcribed answer, evidence quote and offsets, AI rating + rationale, contradiction needing clarification, current/stale state.

Review statuses: `approved | approved_with_changes | requires_follow_up | rejected_result`. These refer to **validity of the AI assessment**, not rejection of the candidate. Each correction must include reviewer, timestamp, evidence/justification and source version. Reviewer may set `insufficient_data` where unsupported. Preserve all history and source snapshot.

Reports must distinguish evidence of professional skill from motivation opinions, separate screening/voice/test data, show missing evidence, and forbid single opaque total score without clearly defined weights and human policy. No automatic hire/reject or auto-shortlist change.

## 8. Retention and privacy

Do not record calls by default. If user/operator lawfully enables recording, track separate recording permission and explicit version. Retention for voice recordings, raw transcript, redacted evidence and auditing is separate, policy-driven and configurable. Restricted deletion procedure must redact personal data while retaining only minimal non-identifying audit where lawful. Retention/deletion must be approved before production activation.

Transcripts may contain sensitive data voluntarily disclosed by a candidate; strip irrelevant sensitive details from AI prompts and reports. Never infer health, religion, family status, age, ethnicity, sex, emotion, accent, personality or other protected traits. GDPR/AI legal review required before production voice decisions. Restrict model/vendor subprocessors by documented DPA and region agreements.

## 9. Logical API contract (for next implementation PR)

- `create_voice_analysis(interview_id, expected_plan_version, expected_transcript_hash, request_key)`: authenticated owner/recruiter; only completed authorized interview, no provider side effects.
- `review_voice_analysis(...)`: optimistic human review with immutable entries. The effective parameter list, the completed-status precondition, and the results-hash check are V7.2; evidence references must match the frozen transcript of that analysis, not a later transcript.
- `list_voice_analyses(application_id, cursor, limit)`: authenticated tenant member; bounded metadata plus redacted evidence, not contact details/recording URL.
- Internal worker RPC: `claim_voice_analysis`, `complete_voice_analysis`, `fail_voice_analysis`: scoped NOLOGIN only; strict schema + lease, not public. These signatures are **proposals**, not implemented endpoints.
- Internal event handler: verifies signed callback and binds provider call/account to tenant/attempt; no direct client callback mutations.

Errors: 401 unauthenticated; 403 owner/recruiter restriction; 404 missing or inaccessible; 409 stale/conflict; 422 invalid transcript/policy; 429 limits; 503 provider/feature disabled. Do not include PII in errors.

## V3 corrections after second Codex review — normative, supersedes conflicting passages

1. LOCKS / SC-006: screening review and retry acquire application-scoped pg_advisory_xact_lock on key 'screening:' + application_id BEFORE any analysis row. The SC-013 architecture must not start an overlapping transaction with analysis row before this advisory lock. SC-010 acquires candidate row with NOWAIT, then owner/member and communication/shortlist/analysis in its audited sequence. These are two existing partial orders that cannot safely be merged by assumption. SC-013-B is **BLOCKED** from any cross-scope locking until SC-010-C delivers one verified global graph and real simultaneous sessions exercising both orders. For standalone voice analysis, use separate transactions that operate only on voice_interview -> transcript -> analysis -> attempt -> review and re-check source freshness through non-mutating controlled checks. Never hold DB row locks during provider API call.

2. PROVIDER RETENTION PROOF: voice_analysis_versions and every voice_analysis_attempt MUST include immutable vendor_retention_approval_id, approval_version, permitted_region, DPA_reference, storage_mode, data_retention_until, effective_from/to and request_configuration_digest. Before each call verify policy is currently approved; after completion persist provider request/correlation ID and deletion receipt status. A later provider policy change never retroactively alters the snapshot. No approved DPA/policy or no deletion capabilities = fail closed.

3. NO CV: Voice analysis external AI payload may contain ONLY privacy-minimized candidate/interviewer transcript segments, rubric/criterion identifiers and minimal fixed reviewed-plan context. The original CV, approved redacted CV, candidate name/phone, screening citation text, recruitment rankings and unrelated candidates are strictly prohibited; do not weaken this rule by calling CV 'untrusted data'. The exact minimized payload is the immutable provider-input snapshot in V7.8, with its own hash and a deterministic map back to source offsets. Do not send the unminimized transcript to close an offset gap.

4. TRANSCRIPT CANONICAL BYTES: adopt RFC 8785 JSON Canonicalization Scheme (JCS) for schema_version and ordered segment array objects, with UTF-8 bytes (no BOM) and SHA-256; forbid unpaired UTF-16 surrogates, NaN/Infinity and duplicate JSON keys. Preserve each original segment text unmodified. Timecodes are integers or explicit null; canonical key ordering and numeric serialization must be RFC8785-compliant. ## V5 — reviewed-successor promotion and explicit review decision RPC (normative)

This section supersedes V3.7 and V4.B to the extent those sections imply replacing a same-source approved analysis when a successor merely completes.

1. **Same-source successor only becomes current after human approval.** A new analysis of the identical frozen transcript, approved plan, rubric and permission source may become completed while the predecessor remains the sole effective current human-approved analysis. A completed successor without review, requiring follow-up or rejected is NOT current. Do not supersede predecessor upon completion alone. In one tenant-scoped transaction on new approved or approved_with_changes decision, lock the interview current-pointer, compare expected version, revalidate unchanged source and authorization, promote newly reviewed successor and mark predecessor superseded. If source/permission changed, do not promote; source invalidation independently makes the predecessor stale immediately. Require a unique (company_id,interview_id) current pointer or equivalent DB guarantee. Test two concurrent approvals, rejected successor, delayed human review and stale inputs.
2. **Decision is mandatory in review RPC.** Decision enum: approved | approved_with_changes | requires_follow_up | rejected_result. approved has no correction rows, approved_with_changes contains one or more audited corrections; follow-up/rejected decisions must never become current even with high ratings. Require a bounded rationale for adverse/follow-up decisions. Evidence always binds the frozen transcript, criterion ID, source version and validated exact offsets. Append review and corrections atomically with server-derived tenant/actor and CAS, including decision in canonical request payload hash; same request key with changed decision conflicts. V7.2 is the effective signature: it adds `expected_results_hash` and rejects every review of an analysis that is not `completed`.
3. **Report guard.** A report may expose the effective result ONLY if interview current-pointer, source hash, latest immutable human review and allowed approval decision all match, and the V7.5 retention, redaction and purge checks pass. Neither completed, nor mere review presence, nor a pointer that names an expired or purged analysis is authorization.

## V7 — pointer lifecycle, completed-only review, and evidence bounds (normative)

This section supersedes conflicting text in §5, §9, §10, V2.4, V2.6, V2.10, V3.7, V3.9, V4.B, V5.2, V5.3 and V6. It does not authorize SQL, migrations, provider calls, recordings, secrets, or production activity. Voice-local transactions still lock only `voice_interview -> voice_transcript_version -> voice_analysis_version -> voice_analysis_attempt -> voice_review`, and never take an analysis lock before `voice_interview`. Cross-module locking stays blocked as in V3.1.

1. **Source change clears and versions the current pointer.** A source change is only a new transcript version, approved plan version, criterion rubric version, or processing permission revision. In that same tenant-scoped transaction, under the `voice_interview` lock: set `stale_at` and `stale_reason = source_invalidated` on every analysis of this interview whose frozen fingerprint differs from the new source; set `current_analysis_id` to null; increment `current_pointer_version` by exactly 1 once per committed change, even if the pointer was already null; set `cleared_reason = source_invalidated`; do not un-supersede or restore a predecessor. A request-key retry of that same change does not bump the version again. `complete_voice_analysis` re-reads the interview source under the same lock order and, when it differs from the attempt snapshot, writes no ratings and no pointer change; a not-yet-completed attempt becomes `failed` with safe code `source_invalidated`. Monotonic `analysis_version` comparison from V6 applies only while the pointer references an analysis with the same source fingerprint. After a clear, the next promotion must send `expected_current_analysis_id = null` and the post-clear pointer version. Sending the cleared analysis id is a conflict and must not compare versions across lineages. Profile, original or redacted CV, screening text, shortlist, ranking, and candidate or application status are not voice inputs: they must not set `stale_at` or change the pointer. A report may apply a separate read-only application-visibility predicate; that predicate does not write voice rows.

2. **Reject review before completion.** Effective signature: `review_voice_analysis(analysis_id, expected_analysis_version, expected_source_hash, expected_results_hash, expected_review_version, expected_current_pointer_version, expected_current_analysis_id, decision, corrected_ratings, evidence_references, rationale, request_key)`. Under the interview and analysis locks, before any review, override, or pointer write, status must be exactly `completed`. `pending`, `processing`, `failed`, `cancelled`, and `unknown` conflict with zero writes. The server recomputes `results_hash` and conflicts unless it equals `expected_results_hash`. `results_hash` is SHA-256 of RFC 8785 JCS bytes of `{schema:'voice-results-v1', analysis_id, items}` sorted by `criterion_id`; each item is `{criterion_id, rating, evidence:[{segment_id, start_utf16, end_utf16, quote_sha256}]}` with evidence sorted by `segment_id`, `start_utf16`, `end_utf16`. Quote plaintext is not written to logs. If status is already `completed`, the same canonical completion payload returns the original result without mutation, including when a review already exists. A different completion payload is PT409 and must not change results or reviews. Approving decisions additionally require, under the same locks: `stale_at IS NULL`, `superseded_by IS NULL`, frozen fingerprint equal to the interview's current source, V7.5 retention checks, and the V7.6 evidence gate. If any approving precondition fails, the transaction conflicts and writes nothing. Non-approving decisions also require `completed` and a matching results hash; they may target a non-current or stale analysis and must not promote it.

3. **Non-approving review of the current analysis clears the pointer.** When `requires_follow_up` or `rejected_result` is committed for the analysis named by `current_analysis_id`, the same transaction sets `current_analysis_id` to null, increments `current_pointer_version`, sets `cleared_reason = review_not_current`, and does not restore or un-supersede the predecessor. A non-approving review of any other analysis does not modify the pointer. The next promotion must expect a null current id and the new pointer version. A later approving review is a new immutable review of the same completed analysis: it may promote only through normal CAS against that cleared pointer. That re-promotion is allowed because this row was not superseded. A superseded predecessor stays ineligible. While the pointer is null there is no current `analysis_version` to compare.

4. **Uniqueness is the current pointer.** V3.7's partial unique index on `completed AND stale_at IS NULL`, and its rule that finalization supersedes the predecessor, are withdrawn. Do not create that index. Several completed, non-stale analyses of one frozen source may coexist while a successor waits for review. The only uniqueness constraint is one current-pointer row per `(company_id, voice_interview_id)`, referencing at most one analysis. `complete_voice_analysis` must not set a predecessor's `stale_at` or `superseded_by`. Supersession happens only in the approving promotion transaction.

5. **Retention and redaction bind every report read and the pointer.** A report read returns no rating, quote, rationale, or other candidate-linked assessment unless the current pointer, source hash, latest allowing review, and approval decision match and every exposed analysis version, criterion result, evidence row, rationale, override, and review is unredacted, unpurged, and still before its `retention_deadline`. A pointer that still names an expired or purged analysis is not authorization. The purge/redaction transaction first, under the interview lock, nulls and version-bumps the pointer when it references the purged analysis or any artifact being purged (`cleared_reason = retention_purge`), with no predecessor restore. It then removes identifying children in FK-safe order. Scope explicitly includes `voice_analysis_versions`, `voice_criterion_results`, `voice_criterion_evidence`, overrides, reviews, rationales, transcript versions, source snapshots, and provider-input snapshots. A remaining tombstone may keep tenant scope and the fact of deletion; it must not keep quote text, transcript text, candidate name, contact data, or a report-visible rating. External provider copies follow the existing deletion-receipt rule.

6. **Human overrides use the completion evidence gate.** `approved` has zero correction rows and rejects a non-empty `corrected_ratings` or `evidence_references`; the server re-validates the stored AI evidence set, including V7.7 limits. `approved_with_changes` re-validates every effective rating after applying overrides, including criteria left unchanged. `below`, `meets`, and `above` each require 1–5 quotes. `insufficient_data` requires zero quotes. Each substantive quote is a non-whitespace exact UTF-16 slice of one `speaker=candidate` segment of the frozen transcript, with matching speaker, hash, and offsets, and must not cross a segment boundary. Exactly one effective rating is required for every frozen criterion. A substantive rating with an empty evidence list fails the RPC. Failure is 422 and zero writes. Client evidence for `approved_with_changes` is the full effective evidence of each changed criterion; omitted evidence for a substantive override is a failure, not permission to inherit a rating that no longer matches.

7. **Versioned quote limits.** Policy `voice-evidence-limits-v1` is stored on the analysis and enforced inside `complete_voice_analysis` and in V7.6. Each quote contains at least one non-whitespace code point, at most 280 UTF-16 code units, and at most 1024 UTF-8 bytes. A criterion has at most 5 quotes and at most 800 UTF-16 code units in aggregate. Measure `end_utf16 - start_utf16` of the validated slice, not a detached client string. Both the per-quote cap and the aggregate cap apply. A violation is 422 with zero partial writes. A later policy version may change the numbers; stored rows keep the policy version they passed.

8. **Provider-input snapshot and offset map.** Before the model call, minimization may split or drop source spans and must not send the unminimized transcript, CV, contact data, or stripped characters. No redaction placeholder token is inserted. The attempt persists an immutable provider-input snapshot: RFC 8785 JCS UTF-8 bytes and `provider_input_sha256` of the exact minimized segments sent to the model, plus a server-only map from each kept provider span to `source_segment_id`, `source_start_utf16`, and `source_end_utf16`. Dropped spans have no map entry. The model does not receive the map, the source offsets, or the stripped text. The analysis version records that `provider_input_sha256`. Completion validates each model citation against the snapshot (`quote === provider_segment_text.slice`) and then stores source coordinates from the map; the source slice must equal the same quote. A citation that does not match the snapshot, that has no map entry, or that would require revealing stripped text, is rejected. A completion whose snapshot hash differs from the reserved attempt is PT409.

9. **Trusted human transcript correction.** Provider ingest accepts only `source_type = provider_asr` from the verified webhook worker. It rejects browser bodies and `source_type = human_correction`. `correct_voice_transcript(parent_transcript_version_id, expected_parent_hash, corrected_segments, rationale, request_key)` is a tenant-checked owner/recruiter RPC with a server-derived actor. It appends a new version with `source_type = human_correction`, `parent_transcript_version_id`, actor, bounded rationale, and its own JCS hash. It does not overwrite the parent, does not clear the current pointer, and does not authorize analysis. `correction_verified_at` stays null. Corrected text remains untrusted model input. `verify_voice_transcript_correction(transcript_version_id, expected_transcript_hash, expected_current_pointer_version, expected_current_analysis_id, request_key)` requires another authorized member of the same tenant, not the corrector. On CAS match it sets `correction_verified_at`, selects that version as the interview's current transcript, and applies the V7.1 pointer clear in the same transaction. A CAS mismatch leaves the correction unverified and the pointer unchanged. `create_voice_analysis` and `claim_voice_analysis` fail closed unless the selected version is `provider_asr` or a verified `human_correction`. Provider-ASR reports keep the provider transcription label. A verified human correction is labeled as a human-corrected transcript and is not presented as provider transcription. Absence of a recording still means no independent audio verification.

10. **Acceptance tests for this section.** In addition to the amended §10 matrix: a change of transcript, plan, rubric, or permission leaves a null pointer and a bumped version, with no restored predecessor, while a profile, CV, shortlist, ranking, or candidate-status change leaves both untouched. Review of `pending`, `processing`, `failed`, or `cancelled` writes nothing. A wrong `expected_results_hash` writes nothing. A divergent second completion writes nothing. Non-approving review of the current analysis clears the pointer; the following promotion conflicts unless it expects null. Two completed non-stale analyses of one source can coexist, and no unique index exists on completed non-stale rows. A report read after deadline, redaction, or purge returns no assessment, including when a pointer was left stale by a fault; the purge transaction itself clears that pointer before child removal. An override to `below`, `meets`, or `above` with zero quotes fails, `insufficient_data` with any quote fails, a quote of 281 UTF-16 code units fails at completion and at review, and quotes on one criterion totaling 801 UTF-16 code units fail both gates. Evidence that matches only the unminimized text, or that maps onto a stripped span, fails. Provider ingest of `human_correction` fails, an unverified correction cannot be claimed, a verifier equal to the corrector fails, and a verified correction clears the pointer.
